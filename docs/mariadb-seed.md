# MariaDB 발표용 시드

`src/main/resources/data-mariadb.sql`은 현재 EFY 엔티티로 생성한 **빈 MariaDB**에 한 번 넣는 발표용 데이터다. 기존 H2용 `data.sql`은 유지한다. 운영 설정의 `spring.sql.init.mode=never`도 유지하며 시드는 수동으로 적용한다.

## 구성과 로그인

공통 비밀번호는 `12341234`이다. 공개된 데모 비밀번호이므로 실제 사용자나 개인정보를 저장하는 서비스에는 사용하지 않는다.

| 계정 | 역할과 시연 내용 |

| `customer1@demo.efy.example` | 견적 대기 요청 3개와 찜 4개 |

총 계정 17개와 고수 프로필 10개를 생성한다. 고수의 제공 서비스·활동 지역은 견적을 보낸 요청과 맞춘다. 서울 전체 활동, 개별 시군구, 경기 전체 활동, 전국 활동을 포함한다.

게시판별 글은 질문 4개, 팁 4개, 구인 3개, 홍보 4개다. 조회 수와 좋아요 수에 차이를 두고 반응이 없는 글도 포함한다. 좋아요·댓글 수는 실제 연결 행 수와 맞춘다.

## 적용 순서

1. `EfyApplication-MariaDB`를 `prod`로 실행하여 테이블을 생성한 뒤 중지한다. 시드를 넣을 때는 앱의 요청이나 예약 정리 작업이 동시에 실행되지 않게 한다.
2. IntelliJ Database에서 **EFY 발표용 MariaDB의 `efy` 데이터베이스**에 연결한다. 기존 BlogRest DB나 H2가 아닌지 확인한다.
3. `data-mariadb.sql`을 이 연결의 SQL 콘솔에서 연다. 한 연결에서 파일 전체를 선택하여 순서대로 실행한다. 첫 오류가 나면 즉시 중단하고 같은 연결에서 `ROLLBACK;`을 실행한다. 오류를 무시하고 다음 구문이나 `COMMIT`을 실행하지 않는다.
4. 시작 부분의 `seed174_empty_guard` 오류는 기존 데이터가 있다는 의미다. 이 경우 기존 데이터를 지우거나 검사를 건너뛰지 않고 적용 대상을 다시 확인한다. 파일 재실행이나 기존 데이터와의 병합은 지원하지 않는다.
5. 성공 후 `scripts/mariadb-seed-check.sql`을 같은 DB에서 실행한다. 첫 결과의 `expected`와 `actual`이 같고 두 번째 결과의 `actual`이 모두 0인지 확인한다.
6. 앱을 다시 시작하고 관리자·사용자·고수 계정으로 로그인하여 목록을 확인한다. 실제 DB에서의 카테고리·지역 중복·동시 요청 검증은 별도로 진행한다.

MariaDB CLI를 사용할 때도 선택한 DB에 파일 전체를 한 번 적용하고 `--force` 옵션은 쓰지 않는다. 외래 키 검사를 끄는 구문, `DELETE`, `TRUNCATE`, 영구 테이블 `DROP`은 시드에 없다. 모든 데이터 INSERT와 집계 UPDATE는 한 트랜잭션으로 묶었다. 고정 ID가 포함되므로 빈 DB에서만 적용한다. MariaDB의 AUTO_INCREMENT가 입력한 최대 ID 다음 번호를 사용하므로 H2의 `ALTER COLUMN ... RESTART`는 넣지 않았다.

## 시연 범위와 주의점

- `CLOSED`는 현재 구현에서 취소 상태다. 별도의 서비스 완료 상태는 만들지 않았다.
- 현재 댓글 모델에는 답글 연결 필드가 없어 일반 댓글만 넣었다. 리뷰·평점도 MVP 제외 방침에 따라 넣지 않았다.
- 사진은 실제 업로드 파일 소유권과 Supabase 저장소 연결이 필요하므로 가짜 파일 ID나 외부 이미지 URL을 넣지 않았다. 프로필·작업·게시글 사진은 실제 업로드 기능으로 추가한다.
- 고수 지갑의 시작 잔액은 데모용 50크레딧이다. 의뢰한 견적당 2크레딧을 차감하고 사용 내역과 `USED` 예약을 맞췄다. 다른 견적은 `RESERVED`다. 실제 결제나 가짜 토스 결제 키는 생성하지 않았다.
- 시드 시각은 적용 시점의 한국 시간이다. 요청은 24시간, 발송 견적은 72시간의 유효기간이 있으므로 오래 두면 시연 화면에서 제외될 수 있다. 발표 직전에 데이터와 실행 상태를 확인한다. 무료 DB의 초기화가 발생하면 빈 DB 여부를 확인한 뒤 다시 적용한다.
- `withdraw` 계정은 탈퇴 시연 후 다시 로그인할 수 없다. 관리자나 다른 시나리오 계정을 탈퇴시키는 용도로 사용하지 않는다.

## 이번에 확인한 결과

2026-11-04에 클라우드 DB와 분리한 임시 **MariaDB 11.2.6**에 현재 백엔드 JAR로 스키마를 만들고 다음을 확인했다.

- 시드 전체 적용 성공과 수량 검사 18항목 일치
- 집계·이름 정규화·매칭·크레딧·채팅·탈퇴 계정 분리 검사 15항목의 불일치 0건
- 이미 데이터가 있는 DB에 재적용하면 첫 데이터 입력 전 빈 DB 검사에서 차단
- 실제 HTTP 138개 요청: 17개 계정 로그인·본인 조회, 게시판 목록·게시글·댓글, 고수 프로필·매칭 요청·견적, 사용자 요청·받은 견적·찜, 채팅 메시지, 관리자 목록, 좋아요 해제·복원, 탈퇴와 이후 로그인 차단

위 결과는 임시 로컬 MariaDB에서의 시드 검증이다. 이후 클라우드타입 `efy` DB에도 최신 시드 전체를 적용하고 COMMIT 완료, 수량 18항목 일치, 정합성 15항목의 불일치 0건을 IntelliJ에서 확인했다. 카테고리·지역 실제 API 검증 결과는 [별도 기록](mariadb-basedata-check.md)에 정리했다. 프론트 화면·WebSocket 전송·결제·파일 업로드는 별도 검증 대상이다.

공통 비밀번호 `12341234`와 수정한 문구를 기준으로 위 HTTP 138개 요청 검증을 다시 통과했다. 클라우드 DB의 시드 관리자 로그인도 HTTP 200과 토큰 발급을 확인했다.

## 문구를 수정한 시드와 기존 DB

- 게시글 15개와 댓글 30개는 작성자의 역할과 글의 주제에 맞춰 작성했다. 서로 다른 사용자의 댓글이 글쓴이의 답변처럼 보이지 않게 했다.
- 프로필 10개는 고수별 작업 범위와 경력을 구분했고 계정 닉네임도 화면에서 사용할 이름으로 바꿨다. 탈퇴 계정의 닉네임은 `최다은`이다.
- 채팅 4개 방의 메시지 24개를 연결된 개발·이사·청소 상담에 맞추고 마지막 메시지 미리보기도 맞췄다.
- 요청서 질문과 답변은 기존 로컬 `data.sql`의 이사·입주 청소·개발 외주 원문을 사용한다. 같은 종류의 요청에는 같은 원문을 재사용한다. 카테고리·지역과 모든 ID·상태·금액·관계는 문구 수정에서 바꾸지 않았다.

빈 DB에는 수정한 `data-mariadb.sql`을 한 번 적용한다. **기존 시드를 이미 넣었다면 전체 파일을 재실행하지 않는다.** 대신 앱을 중지한 상태에서 `scripts/mariadb-seed-text-update.sql`을 `efy` DB에 연결한 한 SQL 콘솔에서 전체 실행한다. 첫 오류에서 중단하고 같은 연결에서 `ROLLBACK;`을 실행한다.

문구 수정 SQL은 계정 이메일·ID·기존 문구가 일치하는 행만 수정한다. 사용자가 직접 바꾼 문구는 덮어쓰지 않으므로 그런 행은 별도로 확인한다. 행을 추가하거나 삭제하지 않으며 재실행해도 같은 문구를 유지한다. 새로운 채팅이 생겼다면 그 대화의 마지막 메시지를 덮어쓰지 않는다.

임시 MariaDB에서 수정 SQL 적용 후 수량·정합성 검사 통과, 재실행 결과 유지, 직접 편집한 댓글 보존, 신규 시드 전체 적용 결과와의 문구 일치를 확인했다. 이 검증에 사용한 서버와 DB는 종료했다.

견적 메시지 27개도 고수별 작업 방식과 전문 분야에 맞게 각각 다르게 작성했다. 이사 고수는 포장·계단 운반·가구 치수, 청소 고수는 창틀·욕실·마무리 확인, 개발 고수는 기능 범위·API·데이터 구조를 구분해 설명한다. 견적이 없는 신규 고수10에게는 메시지를 새로 추가하지 않았다. 메시지의 중복과 요청서 종류와의 대응을 정적으로 확인했으며 이 마지막 문구 변경 후 HTTP 전체 검증을 반복하지는 않았다.
