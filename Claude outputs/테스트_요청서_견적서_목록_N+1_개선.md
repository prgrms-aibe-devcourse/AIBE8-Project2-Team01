# 요청서·견적서 목록 조회 N+1 개선 쿼리 수 검증

- 도메인: 견적·매칭
- 결과: 통과
- 관련: #144, #149

## 확인 범위

- 목록 조회 4개의 실행 쿼리 수를 `@EntityGraph` 적용 전과 후로 비교
  - 고객 내 요청서 목록 `GET /api/members/me/requests`
  - 고수 보낸 견적 목록 `GET /api/quotes`
  - 고객 요청서별 받은 견적 목록 `GET /api/requests/{requestId}/quotes`
  - 고수 받은 요청서 목록 `GET /api/members/me/expert-profile/requests`
- 응답 내용이 적용 전과 같은지

## 확인 결과

| API | 적용 전 | 적용 후 | 적용한 연관 |
| --- | --- | --- | --- |
| 내 요청서 목록 | 9 | 3 | secondCategory, secondRegion |
| 고수 보낸 견적 목록 | 7 | 4 | serviceRequest, 카테고리, 지역 |
| 받은 견적 목록 | 6 | 4 | expertProfile, expertProfile.member |
| 고수 받은 요청서 목록 | 8 | 8 | secondCategory, secondRegion |

- 쿼리 수는 인증 과정의 회원 조회를 포함한 값이다.
- 응답 JSON은 적용 전과 같다.

## 재현 명령과 응답

`application-local`에서 SQL 로그(`org.hibernate.SQL: debug`)를 켜고, 각 API를 한 번씩 호출한 뒤 요청 스레드(`nio-8080-exec-N`)별로 select 수를 센다.

```bash
curl "$BASE/api/members/me/requests" -H "Authorization: Bearer $C"
curl "$BASE/api/quotes" -H "Authorization: Bearer $E1"
curl "$BASE/api/requests/1/quotes" -H "Authorization: Bearer $C"
curl "$BASE/api/members/me/expert-profile/requests" -H "Authorization: Bearer $E1"
```

적용 후 내 요청서 목록 로그: 회원 조회 → `service_request`에 `second_category`, `second_region`을 join한 select 1번. 카테고리·지역을 하나씩 조회하는 select가 사라졌다.

## 발견한 문제와 조치

- 받은 요청서 목록은 같은 구조인데도 시군구 고수에게는 N+1이 없었다. 매칭 조건을 만들 때 고수의 서비스·지역을 먼저 조회해서 같은 카테고리·지역 엔티티가 영속성 컨텍스트에 이미 있었기 때문이다. 전국·시·도 전체 고수는 영속성 컨텍스트에 없는 지역이 섞여 있어 N+1이 발생했고, `@EntityGraph`로 개선했다.
- 쿼리 수만 보지 않고 로그에서 어떤 엔티티를 추가로 조회하는지 직접 확인했다.

## 남은 확인

- 인증 과정에서 회원을 두 번 조회하는 문제는 인증 구조 쪽에서 별도로 검토
