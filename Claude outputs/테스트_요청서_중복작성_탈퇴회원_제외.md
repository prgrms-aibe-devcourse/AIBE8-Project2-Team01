# 요청서 중복 작성 검사 MATCHED 포함 및 탈퇴 회원 요청서 제외 검증

- 도메인: 견적·매칭
- 결과: 통과
- 관련: #142, #143

## 확인 범위

- 요청서 중복 작성 검사: 24시간 안에 같은 소분류로 작성한 요청서가 OPEN이거나 MATCHED이면 차단하고, CLOSED(직접 취소)이면 다시 작성할 수 있는지
- 고수 받은 요청서 목록: 탈퇴 회원(`deleted_at` 있음)이 작성한 요청서가 빠지는지

## 확인 결과

| # | 상황 | 기대 | 결과 |
| --- | --- | --- | --- |
| 1 | 같은 소분류의 OPEN 요청서가 있음 | 409 중복 | 통과 |
| 2 | 같은 소분류의 요청서가 MATCHED | 409 중복 (수정 전에는 201) | 통과 |
| 3 | 같은 소분류의 요청서가 CLOSED | 201 작성 가능 | 통과 |
| 4 | 같은 소분류라도 24시간 지난 요청서만 있음 | 201 작성 가능 | 통과 |
| 5 | 요청서 작성자가 탈퇴 | 고수 받은 요청서 목록에서 제외 | 통과 |
| 6 | 탈퇴하지 않은 회원의 요청서 | 기존처럼 노출 | 통과 |

## 재현 명령과 응답

중복 작성 (customer2, 이사·강남구. 시드의 요청서 9·10은 24시간이 지나 검사 대상이 아님)

```bash
curl -X POST "$BASE/api/requests" -H "Authorization: Bearer $C2" -H "Content-Type: application/json" -d '<이사·강남구 요청서 본문>'
# → 201 (새 요청서 id 11). 4번 확인

curl -X POST "$BASE/api/requests" ...   # 같은 본문 재요청
# → 409 OPEN 중복. 1번 확인
```

```sql
-- H2 콘솔
UPDATE service_request SET request_status = 'MATCHED' WHERE id = 11;
```

```bash
curl -X POST "$BASE/api/requests" ...   # → 409. 2번 확인
```

```sql
UPDATE service_request SET request_status = 'CLOSED' WHERE id = 11;
```

```bash
curl -X POST "$BASE/api/requests" ...   # → 201. 3번 확인
```

탈퇴 회원 제외 (expert1: 이사·강남구 고수)

```bash
curl "$BASE/api/members/me/expert-profile/requests" -H "Authorization: Bearer $E1"
# → customer1 요청서 포함
```

```sql
UPDATE member SET deleted_at = CURRENT_TIMESTAMP WHERE email = 'customer1@example.com';
```

```bash
curl "$BASE/api/members/me/expert-profile/requests" -H "Authorization: Bearer $E1"
# → customer1 요청서 제외, 다른 회원 요청서만 남음. 5·6번 확인
```

## 발견한 문제와 조치

- 메서드를 `RequestStatusNot`으로 바꾸면서 인자를 `OPEN` 그대로 둬서 조건이 반대로 동작했다(OPEN만 통과). 인자를 `CLOSED`로 고쳤다.
- 재테스트 중 H2 UPDATE 대상 ID를 잘못 지정했다(11 대신 12). 응답의 요청서 ID를 다시 확인하고 재테스트해서 통과했다.
